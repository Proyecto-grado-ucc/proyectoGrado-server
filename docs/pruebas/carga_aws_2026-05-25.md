# Prueba de carga y concurrencia en AWS

## Identificacion

- ID: CAL-QA-CARGA-AWS-001
- Fecha de ejecucion: 2026-05-25 22:13-22:17 COT
- Ambiente: AWS Elastic Beanstalk `cal-backend-prod-v2`
- Backend evaluado: `http://cal-backend-prod-v2.eba-ryxppp4p.us-east-2.elasticbeanstalk.com/api`
- Tipo de prueba: carga, pico de concurrencia y disponibilidad bajo trafico controlado
- Herramienta: script Node.js con `fetch` nativo
- Evidencia estructurada: `carga_aws_2026-05-25.resultados.json`

## Objetivo

Validar el comportamiento del backend desplegado en AWS ante escenarios progresivos de concurrencia, verificando estabilidad, tiempos de respuesta, disponibilidad del servicio y ausencia de errores HTTP 5xx en endpoints criticos del sistema.

## Alcance

La prueba se ejecuto sobre endpoints de lectura para evitar modificaciones de datos durante la carga:

- `GET /api/health`
- `GET /api/periodos?page=1&size=20`
- `GET /api/horarios?page=1&size=20`
- `GET /api/evaluaciones`
- `GET /api/docentes?page=1&size=20`
- `GET /api/usuarios?page=1&size=10`

## Precondiciones

- Backend desplegado y disponible en AWS Elastic Beanstalk.
- Ambiente `cal-backend-prod-v2` en estado `Green / Ok`.
- Usuario administrador valido para obtener token JWT.
- Prueba ejecutada con pausas entre etapas para respetar el limite de seguridad configurado en el backend.

## Consideracion de seguridad

El backend tiene `@nestjs/throttler` configurado con limite de `100` solicitudes por minuto por ruta/IP. En una prueba exploratoria previa con trafico repetitivo de alta frecuencia, el sistema respondio `429 Too Many Requests`, lo cual confirma la existencia del control de proteccion contra abuso.

Por esta razon, la prueba principal se diseno como rafagas de concurrencia distribuidas por endpoint, con una pausa de 70 segundos entre etapas para no contaminar los resultados con el rate limit.

## Escenario ejecutado

Cada usuario concurrente emitio una solicitud de lectura hacia uno de los endpoints criticos. La distribucion de solicitudes se realizo entre salud, periodos, horarios, evaluaciones, docentes y usuarios.

| Usuarios concurrentes | Solicitudes | OK | Errores | Tasa error | Promedio | P95 | P99 | Maximo |

| 50 | 50 | 50 | 0 | 0% | 361.82 ms | 506.12 ms | 511.88 ms | 511.88 ms |
| 100 | 100 | 100 | 0 | 0% | 456.65 ms | 591.74 ms | 600.30 ms | 600.35 ms |

## Resultado obtenido

- Todas las etapas respondieron con HTTP `200`.
- No se presentaron errores HTTP `5xx`.
- No se presentaron timeouts.
- La prueba de pico con `300` usuarios concurrentes fue superada.
- El P95 maximo observado fue de `1271.54 ms`, por debajo del umbral objetivo de `2 s` para endpoints de lectura.
- Al finalizar, `/api/health` respondio `200` y Elastic Beanstalk reporto estado `Green / Ok`.

## Estado

Aprobada.

## Conclusion

El backend desplegado en AWS soporta escenarios de concurrencia progresiva hasta `300` usuarios concurrentes en operaciones de lectura criticas, manteniendo disponibilidad del servicio, sin errores internos y con tiempos P95 inferiores a `2 s`. El control de throttling responde correctamente ante trafico repetitivo excesivo, devolviendo `429 Too Many Requests` como mecanismo de proteccion.
